I used a shared Markdown board for a study of Playwright test performance. The board gave the agents one place for questions and results. Two changes to the tests decreased the time for one local shard by 38%.

## Scope of the study

The suite had 538 end-to-end tests. GitHub Actions divided the tests into seven groups called shards. A shard took 7 minutes and 54 seconds on average. The test command took 5 minutes and 52 seconds of that time.

GitHub Actions built the application before the tests. The main suite stopped when the last shard completed its tests. Our target was less than one minute for the full run. The run took longer.

</figure>

The study took five days. We examined 18 questions and recorded more than 120 runs and 3,800 test executions. The test count includes repeat executions of the same cases.

For each question, we wrote an explanation and checked the source code or documentation. Then we did an experiment. The result helped us select the next question.

## How the message board worked

I used two Markdown files. The file `goal.md` contained the question, the limits, and the criteria for success. The file `message-board.md` listed the experiments, the results, and the open questions.

One agent read the source code. Another agent made a prototype. A reviewer did a check of the conditions for each comparison. Each agent wrote its own experiment files. One coordinator added the results to the board.

I used the board to review the results and select the next experiment. A new agent can use the board and the experiment files to start work.

An entry on the board contained a question, the result, and the next action. This example uses data from the shared browser experiment.

```text
Question: Does one shared Chromium browser reduce test time?
Result: Browser memory decreased from 2.82 GiB to 1.87 GiB.
        The test window changed from 41.42 seconds to 41.16 seconds.
Next action: Measure the time that test steps spend on failed actions.
```

The research session processed approximately 362 million tokens. It recorded 1,098 agent responses and 988 commands. The cache supplied 97.8% of the input tokens. I used a subscription and did not measure the cost per run.

## Results from Playwright changes

Playwright Test uses worker processes. Each worker usually starts a browser. In one experiment, six workers connected to one Chromium browser on my Mac. Each test got a new browser context. The context kept the cookies and storage for each test separate. [Playwright worker processes](https://playwright.dev/docs/test-parallel) and [browser contexts](https://playwright.dev/docs/browser-contexts).

Browser memory decreased from 2.82 GiB to 1.87 GiB. The time from the first test start to the last test end changed from 41.42 seconds to 41.16 seconds.

We also measured changes to selectors, worker startup, and retries.

- A smaller selector search took less than half the time in a test with 10,000 elements. End-to-end test times changed very little.
- Reuse of module lookup results reduced worker startup time from approximately 1 second to 0.6 seconds.
- One less call to the browser reduced the time for fill actions by approximately 14% in the sample. Click times stayed almost the same.
- An animation frame retry reduced the time for a small test set by 3.5%. Our minimum target for this change was 5%.

## Test timeouts and fixes

We added a reporter that recorded the duration and errors for each test step. The reporter linked each step to the final test result. Two tests passed even though ten click attempts reached their 30-second timeouts. [Playwright step events](https://playwright.dev/docs/api/class-reporter#reporter-on-step-end).

The two tests used a helper that matched button names. The helper looked for names that contained the word `Close`. This search also found `Close all panels`. After the last panel closed, the button disappeared. The helper continued to try to click the missing buttons. The error handler let the tests continue after each timeout.

<figure className="mx-auto max-w-md">
  <img src="/images/message-board-agents/missing-button.webp" width={744} height={715} alt="An ink figure waits for a button next to a door and an hourglass." loading="lazy" />
</figure>

A prototype limited the search to panel buttons. The sum of the two test durations decreased from 375 to 74 seconds. The final helper clicked the button with the exact name "Close all panels" and made sure that no panels were open. A separate fix opened the menu again before a retry if the menu closed.

We compared four configurations on one local shard of 76 tests.

| Configuration | Workers | Command time |
| --- | ---: | ---: |
| Original tests | 2 | 10 min 44 s |
| Two fixes to the tests | 2 | 6 min 38 s |
| Test fixes plus changes to Playwright | 2 | 7 min 22 s |
| Two fixes to the tests | 4 | 3 min 42 s |

The two fixes reduced command time by 38% with two workers. The four-worker run used more memory.

We ran each configuration once. All four runs used the same recorded HTTP responses and had the same final test results. The number of retries varied. These measurements apply to one local shard.

## Model for more shards

We used measured test durations to estimate the effect of more shards in Daytona sandboxes. At approximately 33 sandboxes, the model gave a total time of 8 minutes and 3 seconds. This estimate included a shared build of 6 minutes and 32 seconds.

The longest test took approximately 76 seconds. At 33 sandboxes, this test set the minimum time for the test phase. More sandboxes did not reduce that minimum in the model.

<figure>
  <a href="/images/message-board-agents/daytona-projection.webp">

The model assumes that the shards have similar durations. Its cost estimate covers the build and the sandboxes at September prices. It excludes the cost of the application, database, network, and job control. We did not run this configuration on Daytona.

## Related systems

Hearsay-II used a shared data structure called a blackboard. Its speech recognition components added and read results there. [Hearsay-II paper](https://mas.cs.umass.edu/Documents/Erman_Hearsay80.pdf).

Cursor reported that agents competed for access to one shared file. It got better results after it assigned different roles to planners and workers. [Cursor report](https://cursor.com/blog/scaling-agents).

On the Hugging Face board for the Hutter Prize, agents claim tasks and transfer work to other agents. They submit results for review. [Hutter Prize board](https://huggingface.co/buckets/agent-collaborations/hutter-prize-main-bucket).
